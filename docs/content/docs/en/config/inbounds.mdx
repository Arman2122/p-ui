An **inbound** is a listener that accepts client connections on a port using a
particular protocol and transport. Most of your day-to-day work is creating and
managing inbounds and the clients inside them.

## Create an inbound

<Steps>

<Step>
### Add an inbound

Open **Inbounds → Add**, give it a remark, pick a **protocol**, and choose a
**port** and listen address.
</Step>

<Step>
### Choose a transport and security

Pick the transport (TCP, WebSocket, gRPC, HTTPUpgrade, XHTTP, …) and the security
layer (none, TLS, or REALITY). See [Transports](/docs/config/transports) and
[REALITY](/docs/config/reality).
</Step>

<Step>
### Add clients

Add one or more clients, each with its own credential, limits, and share link.
See [Clients](/docs/config/clients).
</Step>

<Step>
### Set traffic limit, expiry, and reset

Optionally cap total traffic and set an expiry date for the inbound, and choose a
periodic **traffic reset** schedule: `never` (default), `hourly`, `daily`,
`weekly`, or `monthly`.

For `monthly` resets, select a day from 1 to 31. If the selected day does not
exist in a shorter month, the reset runs on that month's last day.
</Step>

</Steps>

### Bulk actions

Selecting rows in the inbounds table offers **Enable**, **Disable** and
**Delete** for the whole selection. Each inbound is switched the way its row
switch does, and the ones already in that state are reported rather than
touched. A bulk delete removes every deleted tag from the Xray routing
template in one rewrite and prunes the deleted inbounds from the routing
rules in one pass.

## Supported protocols

The inbound editor accepts these protocols:

| Protocol               | Notes                                                                    |
| ---------------------- | ------------------------------------------------------------------------ |
| **VLESS**              | Lightweight; the basis for REALITY + XTLS-Vision. Recommended.           |
| **VMess**              | Older but very widely supported by clients.                              |
| **Trojan**             | TLS-based; supports XTLS and fallbacks.                                   |
| **Shadowsocks**        | Includes Shadowsocks-2022 (`2022-blake3-*`) ciphers.                      |
| **WireGuard**          | Modern tunnel.                                                           |
| **Hysteria2**          | Selected as `hysteria`; the panel emits `hysteria2://` links.             |
| **HTTP**               | HTTP proxy.                                                             |
| **Mixed (SOCKS/HTTP)** | A combined SOCKS + HTTP listener.                                        |
| **Dokodemo-door / Tunnel** | Port forwarding / traffic redirect.                                 |
| **MTProto**            | Telegram MTProto proxy, served by a bundled `mtg-proxy` process (not Xray). Clients get the speed plan and the device cap through the sidecar itself; the inbound can also run the fork's WEB proxy relay for Telegram Desktop, see [MTProto: the WEB proxy](#mtproto-the-web-proxy). |
| **SSH**                | An SSH server built into the panel (not sshd): TCP, WebSocket or WebSocket over TLS. See below. |
| **Kernel WireGuard**   | Selected as `wgkernel`. Served by the host kernel over netlink, not Xray. Needs host setup — see below. |

<Callout type="info">
  Hysteria2 isn't a separate protocol internally — it's the `hysteria` protocol
  with the transport version set to 2, and the panel generates `hysteria2://`
  share links for it.
</Callout>

## Kernel WireGuard (`wgkernel`)

`wgkernel` is a second, separate WireGuard implementation. Instead of Xray's
userspace tunnel, the panel creates a real kernel interface named `pwg<id>` and
programs its keys, addresses and peers directly. Each client is a peer, and the
`.conf` file the panel generates for it is the whole product.

<Callout type="warn">
  There is **no migration path** from a `wireguard` inbound to a `wgkernel` one,
  and the protocol cannot be changed after an inbound is created. Moving means a
  new inbound with a new server key and a new port, which invalidates every
  `.conf` file already handed out. Create `wgkernel` fresh, or stay on
  `wireguard`.
</Callout>

### Requirements

The host kernel must have the `wireguard` module, and the panel must be able to
create network interfaces (`CAP_NET_ADMIN`). Most VPS kernels have both;
OpenVZ and many LXC containers have neither. Where they are missing, the panel
reports the core as unavailable and the inbound editor greys `wgkernel` out with
the reason, so you cannot create one **from the form** — the API still accepts
one, so a scripted deploy or a restored backup can still produce an inbound that
never comes up. The `wireguard` protocol works on those hosts either way,
because Xray tunnels it in userspace.

### Size the interface address up front

Clients are allocated out of the interface address you configure, one `/32`
each, starting at `.2`. A `/24` holds 254 of them, a `/22` holds 1022 and a
`/16` holds 65534 — and the form shows how many are used as you go.

Once the prefix fills, allocation continues in the surrounding `/16`, and every
client out there needs a route of its own that the reconciler rechecks on every
pass. Nothing breaks, but the addressing plan stops matching the interface.

Widening later is safe and the network address does not move. **Narrowing or
rebasing is refused** once clients exist, because the `.conf` files already on
their devices carry the old address and no server can reach in and change them.

### Forwarding and NAT are yours to configure

This is the one real difference in day-to-day operation. An Xray `wireguard`
inbound egresses through Xray, so it needs nothing from the host. A `wgkernel`
device completes handshakes and then **routes nothing** until the host is told
to forward and masquerade its traffic. Run as root:

```bash
printf 'net.ipv4.ip_forward=1\nnet.ipv6.conf.all.forwarding=1\n' > /etc/sysctl.d/99-wgkernel.conf
sysctl --system
```

**Both families, and written to a file rather than set with `sysctl -w`.** A
`-w` lasts until the next reboot, after which the tunnel handshakes and
black-holes again with nothing on any screen explaining why — which is worse
than never having configured it, because by then you believe it is configured.

The `.conf` the panel generates carries `AllowedIPs = 0.0.0.0/0, ::/0`, so the
client installs a v6 default route into the tunnel whether or not the host can
carry it, and a host that forwards only IPv4 drops every v6 flow in silence.

Then NAT, in its own table so it can be removed whole and cannot entangle with
rules you already have:

```bash
nft add table ip pui_nat
nft 'add chain ip pui_nat postrouting { type nat hook postrouting priority srcnat; policy accept; }'
nft add rule ip pui_nat postrouting iifname "pwg*" oifname != "pwg*" masquerade
```

**Match the device, not the subnet.** `iptables -t nat -A POSTROUTING -s
10.0.0.0/24 -j MASQUERADE` covers exactly one range, so every additional
`wgkernel` inbound on a different range silently needs another rule nobody
reminds you to add. `iifname "pwg*"` covers every one of them, present and
future, and excludes peer-to-peer traffic between clients on the same inbound.

Add the v6 twin with `nft add table ip6 pui_nat6` and the same rule if you
masquerade IPv6; with a routed v6 prefix, forwarding alone is enough. If the
host has no IPv6 at all, tell your users the tunnel is v4-only.
`GET /panel/api/egresses/preflight` reports both forwarding knobs.

The nftables rules do not survive a reboot on their own. The panel deliberately
does not write firewall rules for you, so persist them yourself — either through
your firewall's own mechanism, or with a unit of about six lines:

```bash
nft list table ip pui_nat > /etc/p-ui/nat.nft
cat > /etc/systemd/system/p-ui-nat.service <<'EOF'
[Unit]
Description=p-ui wgkernel NAT
After=network-pre.target
Wants=network-pre.target
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/sbin/nft -f /etc/p-ui/nat.nft
[Install]
WantedBy=multi-user.target
EOF
systemctl enable --now p-ui-nat.service
```

`network-pre.target` rather than `network-online.target`: the rules should be in
place before an interface carries a packet, not after.

An inbound attached to an **Egress** (below) still needs the forwarding sysctls,
but not the NAT rules.

### Egress

An **egress** sends one `wgkernel` inbound's decrypted traffic out through a
named Xray outbound or balancer instead of the server's own address — a warp
exit, a chained proxy, another VPS. Create one under **Xray Configs → Outbounds**
by picking a protocol a core exits on, then point a routing rule at it. The panel owns one `ip rule`
per routed inbound, a private routing table and its blackhole; the front device
belongs to Xray. Everything the kernel needs is derived from the egress id, so an
id is never reused.

- **The NAT table above is not needed for a routed inbound.** Xray
  terminates the connection and dials the destination itself, so there is nothing
  to NAT. Forwarding is still required — it is a precondition of any L3 inbound
  reaching anything at all — so keep `net.ipv4.ip_forward` and its v6 twin on.
- **It is master-local.** An inbound deployed to a node cannot be routed through
  one: the egress id is a global database key while the routing table, rule and
  front device it derives all live on one host.
- **A dark egress contains; it never leaks.** If the target names no outbound, if
  the egress is switched off, or if Xray has not yet created the front device, the
  private table holds only its blackhole and the attached traffic is dropped. It
  does not fall back to the server's own identity — that is the whole point of the
  feature, and it is why the panel refuses to disable or delete an egress that a
  routing rule still sends traffic to.
- **Do not test one with `ping` or `traceroute`.** ICMP is echo-only and answered
  by the front device itself, so a ping through an egress succeeds for a
  destination that exists nowhere — including when the egress is completely dark.
  Termination also changes what a TCP connection looks like: one to a dead host
  completes its handshake and only then RSTs. Test with a real request from a
  connected client instead, e.g. `curl https://ifconfig.co`.
- **`GET /panel/api/egresses/preflight`** reports what stops this host carrying an
  egress: a foreign object in the reserved band (routing tables 30001-30999, rule
  priorities 31001-31999), strict reverse-path filtering, forwarding left off, and
  any enabled egress whose front device is not up yet.

### Other things to know

- **`limitIp` does nothing** for this protocol. The per-client IP limit is
  enforced by reading Xray's access log, and a kernel device produces none. The
  field is still stored; it simply is not applied.
- **Stopping the panel leaves the devices up.** That is intentional — tunnels
  survive a panel restart or upgrade. A permanently removed panel leaves its
  interfaces behind; delete them with `ip link del pwg<id>`.
  Traffic that moves while the panel is down is not billed.
- **Do not add your own routes on a `pwg<id>` device.** Reconciliation owns that
  device's route table and removes routes it did not install. Put extra routes
  on another interface.

## SSH (`ssh`)

An SSH server built into the panel, not sshd. It offers `direct-tcpip`
forwards, the dynamic (SOCKS) forwarding every SSH client app uses, on one of
three transports per inbound:

- **TCP** — a plain SSH port.
- **WebSocket (HTTP)** — one port that answers both the bare `101` upgrade the
  HTTP Injector family sends (raw SSH follows the status line) and a real
  RFC 6455 upgrade, so a CDN can sit in front. A **path** limits what is
  accepted; empty accepts any.
- **WebSocket over TLS** — the same over TLS, with the certificate and key
  files named on the inbound. The pair is re-read when it changes, so a renewal
  needs no restart.

To share port 443 with REALITY, keep this inbound on a local port and point an
Xray inbound's fallback (with a path) at it.

Each client gets a **username** — a short login name; an email is not one,
since `@` breaks `ssh://` links and Injector payloads — and a **password**,
both minted when left empty. The panel enforces, inside the server:

- **Quota and expiry**: a depleted or expired client is refused, and its open
  sessions are closed.
- **IP limit**: counted as distinct source addresses at login, so the extra
  device is refused before it connects. Sessions are also reported with their
  source, so the IP-limit job sees them like every other core's.
- **Speed plan**: applied as a per-client rate on every forward, both
  directions. This is the first kind outside the kernel-WireGuard family whose
  clients carry a rate, because the server counts the bytes itself.

The client's config is served as a text file through the subscription file
route (host, port, username, password, transport, path and the Injector payload
template), and the subscription list carries an `ssh://` link for the apps that
import one.

**UDP.** With **UDP through the tunnel (UDPGW)** on, the inbound answers badvpn's
udpgw protocol on a loopback port inside the tunnel (7300 by default), which is
how HTTP Injector, HTTP Custom and NapsternetV carry UDP (games, calls, DNS)
over SSH: the app is given `127.0.0.1` and that port as its UDPGW address.
Nothing else listens on the host; every datagram is billed and rate-limited to
the client like a TCP forward, DNS-flagged datagrams go to the server's own
resolver, and destinations follow the same policy as TCP forwards. Routed
through Xray, the datagrams follow the routing rules like any TCP forward.

**Forward policy.** A forward cannot reach the server itself or a private
network: loopback, link-local, private and reserved ranges and the host's own
addresses are refused, after resolving a name, so the panel's own services are
never one forward away. The server offers an ed25519 and an RSA host key, cuts
off a handshake that never finishes, drops a peer that stops answering
keepalives, and caps open forwards per connection.

**Routing.** By default an SSH inbound dials its forwards straight out, and no
routing rule can name it. Turn on **Route forwards through Xray** and the panel
gives that inbound a loopback bridge into Xray's router, so it becomes a
routing subject like any other inbound and a rule can send its traffic through
an exit. It is the same bridge MTProto uses, so the same two consequences
apply: Xray becomes required, and while it is down forwards are refused rather
than leaking out of the server's own address; and the Xray template's own
rules, ad blocking and the private-address block, begin applying to this
traffic.

Rules on an SSH inbound may match address, port, network and domain. A client
using dynamic forwarding sends a hostname, so a domain rule works; source and
source-port rules do not, because Xray sees every one of these connections as
coming from the panel on loopback, and the editor does not offer them.


## TUIC (`tuic`) and AnyTLS (`anytls`)

Two protocols Xray does not serve, run by the bundled **sing-box**: one
sing-box process per inbound, supervised by systemd as the `p-ui-core` user
(a system user with no shell that the installer creates) and kept alive
across panel restarts and updates. The binary is compiled from upstream's
tagged source at release time, because the published build omits the stats
service the panel bills from; nothing in it is patched.

- **TUIC** rides on QUIC over **UDP**, with the congestion control you pick
  (`bbr` for lossy links) and an optional 0-RTT handshake. Each client has a
  **uuid** and a **password**.
- **AnyTLS** is TLS over **TCP** with a padding scheme; each client has a
  **password**.

Both are TLS-only, so the certificate and key files are named on the inbound
along with the server name clients verify. The daemon reads the panel's own
copy of the pair, which it can open as its user; a renewed certificate is
picked up without a restart.

What the panel enforces, and how:

- **Quota and expiry**: a depleted or expired client is disabled and the
  daemon reloads without it. Per-client traffic comes from sing-box's stats
  API; the counters are drained before every reload, so a reload costs
  nothing that was already moved.
- **IP limit**: live connections are read from sing-box's daemon API with
  their source, so the IP-limit job sees them like every other core's.
- **Speed plan: not available.** sing-box has no per-user rate control and
  its clients share one socket, so a speed plan does not apply on these
  kinds; the form says so.

Client edits land on the daemon's next pass, **within 10 seconds**: sing-box
has no hot user add, so an edit is a config rewrite and a reload, coalesced.
The save tells you when that is the case. A change to the port, the address
or the TLS pair restarts the process.

The subscription carries a `tuic://` or `anytls://` link the client apps
import (sing-box, Clash Meta, NekoBox, v2rayN). QUIC needs larger socket
buffers than the kernel default; the installer sets them in
`/etc/sysctl.d/99-p-ui-quic.conf`.


**Routing.** By default the daemon dials destinations itself and no routing
rule can name this inbound. Turn on **Route traffic through Xray** and the
panel gives it a loopback bridge into Xray's router, so it becomes a routing
subject like any other inbound and a rule can send its traffic through an exit.
Two consequences: Xray becomes required, and while it is down this inbound
carries nothing rather than leaking out of the server's own address; and the
Xray template's own rules, ad blocking and the private-address block, begin
applying to this traffic.

Rules on one of these inbounds may match address, port, network and domain.
Source and source-port rules do not work, because Xray sees every one of these
connections as coming from the daemon on loopback, and the editor does not
offer them.


## OpenVPN (`openvpn`)

The distribution's OpenVPN (2.5 on Ubuntu 22.04, 2.6 on 24.04 and Debian 12),
one supervised process per inbound, run as `p-ui-core` under systemd with only
the capabilities a tun server needs. The installer adds the `openvpn` and
`openvpn-auth-radius` packages.

Identity is **CA-free**. On the first save the panel mints the server's
certificate and its tls-crypt-v2 server key and keeps both in the inbound's
row (a database restore is a complete restore). Clients pin the certificate by
fingerprint, so no CA ships in a profile, and every client carries its own
tls-crypt-v2 key wrapped by the server key: nobody without a panel-issued
profile gets a handshake, and a removed client is refused at login. Clients present no certificate; they log in with a **username**
and **password**, minted when left empty.

Logins go through the panel's embedded RADIUS server via the plugin, which is
also where traffic and sessions come from:

- **Quota and expiry**: a depleted, expired or disabled client is refused at
  login and its open sessions are ended through the management socket.
- **IP limit**: counted as distinct source addresses over live sessions, so the
  extra device is refused at login; sessions are also reported with their
  source and tunnel address, so the IP-limit job sees them.
- **Speed plan**: applied per client on the tun device by tunnel address, the
  way kernel WireGuard's is. Each client keeps a stable tunnel address across
  reconnects.
- **Routing**: the inbound's decrypted traffic appears on `pov<id>`, so
  routing rules select it like kernel WireGuard's.

Accounting counts link bytes (encrypted, with control traffic), not payload;
expect a few percent more than an Xray client moving the same data. The
subscription serves the client's `.ovpn` file; there is no link form. One
process serves one transport: for UDP and TCP on one host, create two
inbounds. DCO is off on the 2.6 line, whose counters under it are not to be
trusted.


## OpenConnect (`ocserv`)

The distribution's `ocserv`, one supervised process per inbound, serving the
AnyConnect protocol over TLS and DTLS on a single port. The installer adds the
`ocserv` package and masks the units it ships: Debian starts it
socket-activated on 443, which would take that port from the panel's own
inbounds.

The daemon's privilege model is its own, and it is not OpenVPN's: the process
serving each connected client runs as `p-ui-core`, while the main process and
the authentication helpers stay root, because they create the tun devices and
own the control socket. The unit therefore runs as root and grants no
capabilities.

Everything about a client comes from the panel's embedded RADIUS server, and
the daemon keeps no user database, so adding or removing a client writes no
file and reloads nothing. That reply carries the tunnel address, the DNS
servers, the routes and the speed plan, which is why the panel writes
`groupconfig=true` into the daemon's auth line: without it the login still
succeeds and everything else in the reply is dropped.

- **Quota and expiry**: a depleted, expired or disabled client is refused at
  its next login, and its open session is then ended through `occtl`. Both
  halves are needed and in that order — the session cookie stays valid, so a
  client disconnected while it would still be admitted simply reconnects.
- **IP limit**: counted as distinct source addresses over live sessions, so the
  extra device is refused at login.
- **Speed plan**: enforced by the daemon itself, handed over at login. A
  changed plan therefore reaches a client at its **next connection**, not
  mid-session.
- **Routing**: available, selected by the inbound's own **subnet**. Every
  session gets its own short-lived kernel device, so no interface name is
  stable enough for a rule; the pool the inbound hands addresses from is, and
  a rule naming this inbound sends everything sourced in that pool through the
  chosen exit. Rules may match address, port, network and domain. Two pools
  that overlap are refused at save: each installs its own kernel rule, and over
  the addresses both cover one inbound's clients would leave through the
  other's exit.

Identity is a **server certificate and nothing else** — clients present none
and log in with a **username** and **password**, minted when left empty. On the
first save the panel mints a self-signed certificate and keeps it in the
inbound's row; the profile it serves pins that certificate's public key, which
`openconnect` understands. The official Cisco AnyConnect app does not pin: for
it, paste a certificate and key your clients already trust into the inbound's
own fields, and the profile then carries no pin.

**Camouflage** is worth turning on where the protocol itself is filtered. The
daemon answers every request that does not carry the secret exactly as a web
server would, so a scan finds nothing; the secret is minted on save and rides
each client's URL after a `?`. It needs ocserv 1.2 or newer, which is what
Ubuntu 24.04 and Debian 13 ship; on an older one the panel refuses the save
and names the version, because that daemon accepts the option, prints
"skipping unknown option" and serves the inbound in the clear.

Accounting is exact per session and cumulative, read from the daemon's own
accounting records rather than from interface counters, so it survives a
reconnect. The subscription serves the client's config file; there is no link
form.


## Fallbacks — multiple protocols on one port

Fallbacks let a single TLS port (e.g. `443`) serve more than one protocol — for
example VLESS **and** Trojan — by routing unmatched handshakes to a child
inbound. In Penhoon UI, fallbacks are managed in the panel (a master inbound's
**Fallbacks** list) rather than hand-written into JSON.

Fallbacks are available only when the master inbound is:

- **VLESS** or **Trojan**,
- on the raw **TCP** transport,
- with **TLS** or **REALITY** security.

Each fallback rule targets a child inbound and can match on `path`, `alpn`, and
`dest`. Client share links for a fallback child are automatically rewritten to
advertise the master's address, port, and TLS.


## MTProto: the WEB proxy

Telegram Desktop 7.1 added a **WEB proxy** connection type: the client loads a
page from your hostname inside its own WebView over real HTTPS, and that page
carries the MTProto stream inside a WebSocket. To the network it is a browser
visiting a website. Only Telegram Desktop offers this type; phones and the web
clients keep using the FakeTLS link.

The bundled `mtg-proxy` serves it as a **second process** beside the proxy,
reading the same generated config. Turn it on in the MTProto inbound's form:

| Field | Meaning |
|---|---|
| **WEB proxy** | Runs the relay for this inbound. Off by default. |
| **Hostname** | The bare name clients type, for example `web.example.com`. It must carry a browser-trusted certificate on port 443; changing it invalidates every WEB link ever issued. |
| **Cover site directory** or **upstream** | What everyone who is not a Telegram client sees. Exactly one: a directory of files to serve, or an `http://` upstream to reverse-proxy. Nothing ships as a default, on purpose: a default page every operator installs is a fingerprint. |

The panel owns the rest: the relay's signing key, its two loopback ports, its
lifetime (started with the proxy, restarted within ten seconds if it dies,
stopped when you turn it off), its logs on the Cores page under the inbound,
and its health. An inbound whose relay is down shows as **degraded** with the
reason.

### What you provide

The client fixes the port to 443 and validates the certificate like a browser,
so three things are yours:

1. **A real certificate for the hostname on port 443.** The panel has no ACME.
2. **A front proxy** on 443 that terminates TLS and forwards the **whole
   hostname** to the relay's loopback port with **PROXY protocol v2**. The form
   shows the port after the first save. Without the PROXY header the relay
   refuses every stream, deliberately: behind a front proxy every connection
   would otherwise look like `127.0.0.1`, and the device cap would count nothing.
3. **The cover site** from the table above.

The fork's own documented front is Caddy. With Caddy owning port 443 for the
hostname:

```caddyfile
web.example.com {
	log {
		output discard
	}
	reverse_proxy 127.0.0.1:RELAY_PORT {
		transport http {
			proxy_protocol v2
			read_timeout 0
			write_timeout 0
		}
	}
}
```

Replace `RELAY_PORT` with the port the form shows. `log { output discard }` is
not optional: the bearer for a live session travels in a header, so an access
log on this hostname writes live credentials to disk. If Xray already owns port
443 on the same address, put an SNI router in front or give the relay's
hostname its own address; a REALITY inbound cannot front it.

### Links

An MTProto client of an inbound with the relay on gets two links: the usual
`tg://proxy` one and a `tg://webproxy?server=<hostname>&secret=dd…` one carrying
the same key in the `dd` spelling and no port. The WEB link's parameter names
mirror `tg://proxy` and have not been confirmed against a real client; if the
link does not take, the hostname and the `dd` secret are exactly what the
client's own two fields ask for.

### Checking it without a client

From a shell you can confirm the relay serves the cover site to everyone
without a credential, and answers a wrong one with the same bytes:

```bash
diff <(curl -sS https://web.example.com/) <(curl -sS 'https://web.example.com/?bridge=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA')
```

No output means the two are identical. Whether a real Telegram Desktop
connects, loads media and survives an idle period is something only the client
can tell you; the panel cannot prove it.
