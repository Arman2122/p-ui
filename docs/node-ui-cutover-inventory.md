# Master UI cutover inventory

Read-only inventory, 19 October 2026. No legacy routes, controls or schemas were removed. The master business factory and native qualification gates remain closed. Existing fleet APIs and test fixtures do not establish production availability.

The placement service currently preserves arbitrary resolved runtime IDs but reports `RUNTIME_ALIAS_UNQUALIFIED` until compiler mapping is qualified. Multiple same-family bases also block application. Capability inventory is universal across configured workers of the same family; it is not permission to invent a canonical worker or ignore an ambiguous base.

## Creation and edit construction

- `ClientFormModal.tsx:578` constructs a single flat client payload. `clientPayload.id` is a transport UUID. It adds credential fields according to the legacy `/cores` credential manifest and sends selected inbound IDs, policy ID/overrides and external links through the `save` callback.
- `useClients.ts:326` posts `/clients/add` through `ClientCreateRequestSchema`. That handwritten schema currently has no operation ID, source revision or per-binding credential structure; unknown top-level fields are stripped. Edit posts `/clients/update/:email` without source CAS metadata.
- `ClientsPage.tsx:934` sends a second external-links write for non-plan creation although links were already included in the creation body. Edit always sends external links separately. An atomic owned creation/edit flow cannot keep these follow-up mutations.
- `ClientBulkAddModal.tsx:207` creates fresh UUIDs, passwords and auth values on each submit. Bulk retry therefore does not preserve an exact request, and the modal closes after the reported batch result. Bulk/import/rotation need their own durable per-item contract before being routed as owned operations.
- `ClientFormModal.tsx:427` and the bulk form choose the first selected SS2022 method. The single-client effect at line 489 remints the shared password when it does not match that method, including editing. One flat password cannot safely express mixed 16-byte and 32-byte SS2022 bindings. Hydration currently flattens `credentials` into `ClientRecord`; it does not expose a per-binding credential editor.

## Reliable metadata and proposed creation boundary

The authenticated `useSignedInUser()` query (`/panel/api/me`) establishes administrator/reseller access. Browser `window.PUI_ROLE` holds that authentication role, not the process role `master|node|combined`. For an existing owned client, `traffic.accounting.source === 'fleet'` plus `accounting.clientId` provides its immutable fleet identity, including dormant terms. Numeric `ClientRecord.id`, email and the transport UUID are different identities.

There is no current frontend process-role or owned-creation capability field. `FleetStatus.ready` establishes listener readiness, not business-factory support. Fresh creation should either dispatch through a server-owned common-route decision or use explicit server-provided creation capability metadata; it cannot infer ownership from an absent client, a populated node list or a ready listener.

The proposed owned creation contract is one generated request containing an operation UUID, normalized source/policy/group/attachment/external-link intent, and deliberate credential inputs per binding (or an explicit server-generation policy). One transaction must validate all bindings, create the source and owned identity, persist compatible credentials and durable work, and return immutable fleet client ID, source revision and pending outcomes. It must not invoke a core, generate host identity, or silently replace explicitly supplied credentials. Mixed SS2022 requirements must be rejected unless separately representable; OpenVPN node-derived wrapping must remain explicit and unavailable for forwarding until fulfilled.

Secret-bearing requests remain frozen in memory for exact retry. Browser persistence may retain only a nonsecret operation/receipt locator; passwords, private keys, TLS-crypt material and other credentials must never be copied into session storage. After reload, resolve the server receipt/current identity instead of regenerating a new operation or new secrets. An unknown receipt must remain unresolved rather than implying success or permitting an automatic replacement identity. The owned path must skip the extra external-links POST. General edit, attach/detach, group/LDAP operations and bulk/import are separate integration gates.
