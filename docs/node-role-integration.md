# Role integration contracts

The role boundary is usable only with an owned fleet runtime and all five mixed-job handlers. `main_role.go` intentionally returns `web.ErrFleetRoleServices` until these dependencies are complete. Supplying legacy jobs, no-op callbacks, or a callback that discards a failed mutation does not satisfy this contract. Master and combined must use identical management callbacks.

Legacy database restore refuses explicit fleet roles, an existing control configuration, persisted fleet authority or nodes, owned clients, and a recovery-required fence. Unknown configuration or database state also refuses. The check is the first operation in `restorePostgresDump`, before that method invokes restore tools, spools the archive, takes a safety dump, changes local cores or closes the database; backup export remains separate. This protects configured or persisted fleet state. Importing a fleet backup into an empty target and simultaneous first initialization still require a complete recovery/cutover workflow; this guard does not qualify either operation.

## Runtime and factory

The root business bridge supplies `service.NewFleetRuntime(db) (runtime.Runtime, error)`. It must turn normalized panel intents into durable UUID-based fleet operations, preserve shared client identity and authority, and reject legacy integer-node dispatch. `web.WithFleetRoleServices` accepts this runtime plus `FleetRoleJobs`:

```go
GroupMembership      cron.Job
LDAP                 cron.Job
InboundTrafficReset  map[string]cron.Job // inbound displays only; hourly, daily, weekly, monthly
OutboundSubscription cron.Job
Stats                cron.Job
```

The factory must validate each dependency before enabling the role. Missing or typed-nil handlers fail before core creation, cron creation or HTTP startup. `StartPanelOnly` follows this same boundary. Master shutdown and SIGUSR1 cannot stop or restart node daemons. An unset role temporarily retains the ordinary panel; it is not a master-only shortcut.

The runtime constructor now exists for explicit enable/disable commands. It binds the current root PostgreSQL handle and pool, requires a same-pool caller transaction, and rejects a replaced database before and after the source mutation. The old post-commit runtime commands return typed unsupported-operation errors; they do not fall back to local or legacy node calls. Local PostgreSQL rollback/replay/authorization/replacement tests and both removed lifecycle guards pass. The production factory remains gated on the other owned adapters and jobs. Panel restart now reconstructs role services instead of reusing the pre-restore options. The role's context is cancelled before panel shutdown and recreated for restarted jobs.

## Group membership

The existing `ClientService.ConvergeGroupMemberships` reads missing `group_inbounds`/`client_inbounds` attachments, invokes `BulkAttach`, and may set the local Xray restart flag. It cannot be installed as the fleet callback.

The source bridge must expose an owned attachment operation that accepts the authoritative client identity and inbound membership intent, rechecks group/plan/reseller eligibility in its transaction, updates normalized joins, invalidates stale placement/source digests, and queues approved node graph reconciliation. The operation must be idempotent on an already-attached client and cannot regenerate credentials. It must return per-client failures and durable pending status. Group convergence may batch and page the missing joins, but cannot silently mark an attachment complete before the owned operation accepts it. Planned/automatic placement selection remains the bridge's responsibility.

Legacy membership moves, group rename/delete, quota edits and shared-template edits now refuse current owned clients and retained term/group-budget provenance. Their database guards lock normalized clients before group parents, revalidate membership after parent serialization and refuse newly appearing source IDs. Derived groups receive a zero-baseline serialization parent; quota edits recheck its original ID and name. Group quota and template metadata commit together. The legacy attachment commit paths also protect every current/incoming client in that inbound, so editing a legacy neighbor cannot rewrite an owned source through the full inbound synchronization. These guards preserve the existing legacy per-inbound partial-success behavior; they do not provide an owned group-edit adapter. Owned moves/renames remain gated pending stable group-ID command binding and an explicit term boundary.

The bounded guard gate passed real PostgreSQL race tests, including ownership adoption, a newly appearing member, owned-neighbor attachment refusal, lock order and quota/template rollback (final affected selection 44.429 seconds). All ten removed-safeguard controls reproduced, and scoped service/entity lint reported zero issues. The desired-source reader separately passed its bounded credential race selection in 15.239 seconds and seven semantic controls. These checks do not qualify production factory activation or active-term editing.

Required tests drive actual PostgreSQL joins: duplicate concurrent ticks create one attachment; a failed source transaction leaves neither a normalized attachment nor a published graph; changed group rights cannot attach a client; repeated group membership does not allocate a second quota/rate allowance; partial batch failures remain retryable and visible. No Xray restart flag or local runtime is permitted.

## LDAP

The existing LDAP job calls normalized create/enable/detach services and schedules local restarts. Its decision rules must survive the role replacement: positive flags enable only accounts actually attached to configured tags; negative flags disable panel-wide; auto-delete affects only LDAP-created clients; the first complete fetch records a baseline and does not delete; an empty or less-than-half fetch never advances that baseline or deletes clients.

Required bridge operations are owned create-and-attach, enable/disable, and detach. Each must fence current placement and credential generations and queue node updates, including stops for removed authority. LDAP-origin stamping must be atomic with creation so an existing administrator-created identity is never adopted accidentally. Read failures cannot become empty authoritative snapshots. The callback must retain its successful-fetch baseline across ticks, and must return errors for failed mutations. Callback construction must fail if any enabled LDAP mutation lacks its owned implementation.

Tests need a controlled LDAP response plus real PostgreSQL source operations: directory outage/empty/partial snapshots retain clients; a restarted callback establishes a fresh baseline; manual accounts survive auto-delete; enable scope and global disable semantics are preserved; a node that is offline retains old reserved authority until the stop is acknowledged.

## Shared client allowance resets

The user selected one plan/client reset schedule. The owned scheduler and API are implemented in `fleet_reset_schedule.go`, `fleet_reset_execution.go`, and `fleet_reset_scheduler.go`; [the reset contract](node-reset-schedule.md) describes cadence, operation receipts, cancellation, and validation. This replaces the earlier uninstalled calendar-slot adapter. No per-inbound job may reset a shared client's allowance.

A nullable client override inherits the applied plan. The persisted UTC anchor supports hourly, daily, weekly, and monthly schedules, retaining the original month day across short months. Policy edits do not create terms or credit. A partial due index and bounded pages keep the original operation referenced while drain is pending; retry eligibility is separate from the original due time. The worker belongs to `RunFleetAuthoritySchedulers` and is cancelled with the control-plane lifecycle.

Beginning a reset marks the predecessor draining and queues real source-stop work atomically. Completion requires every old grant's actual applied stop and settled zero rates. It preserves expiry, measured history, and old reservations, then clears old placement grant pointers and queues authentication-only source publication. Fresh demand obtains new-term credit. Missed intervals advance once beyond completion instead of minting repeated allowances. Concurrent completion for clients in the same group takes an exclusive group-row lock before snapshot/history projection to avoid the reproduced SHARE-lock upgrade deadlock.

Source or credential drift leaves visible pending work. Explicit administrator cancellation names the exact pending operation, preserves the original allowance and mandatory stops, skips its due interval, and retains linked receipts. Configuration and cancellation dispatch through the owned runtime, with operation UUID replay, expected revisions, current database checks, and audit records.

Real PostgreSQL tests cover the scheduler, two-node applied stops, rollback, post-close source publication/APPLIED/fresh demand, inherited policy, cancellation and grouped concurrent completions. The master factory remains gated by the other business prerequisites and Linux/release qualification. The separate `InboundTrafficReset` callbacks still require an owned display-counter implementation; supplying legacy client-reset jobs is not acceptable.

## Stop publication

`controlplane.Store.StopConfiguration` accepts a durable operation UUID, exact applied base revision and SHA-256, selected grant UUIDs, and the owned authority/credit delivery validators. It requires the current desired and applied revisions to match the supplied base. An exact operation retry returns its recorded result even after a later publication; a changed request under the same operation UUID conflicts. The service caller must retain the operation identity while the stop awaits its applied receipt.

The operation composes the frozen base with current authority and credit outboxes, including initial grants delivered only through authority deltas. It preserves unrelated configuration, descriptors, credentials and file assets; selected grants become disabled with zero desired rates. It keeps quota reservations, usage and outstanding rate authority until the node acknowledges application. Ambiguous or blocked unrelated latest authority returns `ErrStopComposition` without changing the node. There is no source rematerialization, acknowledgement fallback or bypass on ordinary publication.

The caller must enter with no target source, client or pool locks held. Stop composition locks all normalized panel client rows in ascending order, then all logical fleet client UUIDs in ascending order, before invoking validators; it locks selected rate pools in ascending UUID order before changing shares. A selected grant may stop using proven frozen ownership even when its source or placement is stale. Pending enabled authority for unrelated grants must still pass the current owned validators. Already acknowledged frozen authority remains valid carry-forward evidence.

If the exact base has one compilation provenance record, the stop carries its compilation UUID to the new deployment under the stop operation UUID. Missing provenance remains absent; foreign or ambiguous provenance is rejected. The original compilation and binding manifest remain unchanged, so a stop cannot prove that a native address has disappeared from the graph.

Known provider bindings carry forward only when every frozen manifest pin matches the exact base node, installation, runtime, compilation, cache revision/digest and follow policy. Missing, unknown or conflicting rows are refused. Both deployment revisions must prove their own runtime projection hashes, while provider graph bytes, file assets and admission descriptors remain unchanged. New binding rows reference the stopped revision and remain pending for a later APPLIED provider wake; no current provider, source or defaults are read.

Publication requeues ongoing credit work. Only an exact applied full baseline can remove covered older authority/credit outboxes, using revision and payload comparisons that retain concurrent newer rows. A received receipt is insufficient. Stop proofs are recorded only for the current desired applied revision; an old disabled receipt cannot resurrect proof while a newer enabling publication is pending. Reconciliation must await these actual applied proofs before completing a term transition or treating a source disable as drained.

## Outbound subscriptions

The old refresh path is not safe to reuse: `RefreshAllEnabled` invokes `fetchAndStore`, which can fetch through the panel's local Xray egress, validate against a local core binary, overwrite provider cache rows, and call `RoutingService.PruneOutboundForCurrentTemplate`. Its cron wrapper then requests a local restart.

The provider candidate now has a lifecycle-bound configuration/refresh service, immutable cache revisions, explicit node/shared credential scope, provider-aware network version 2, an indexed publication binding projection, bounded fanout cursors, and a separate node rollout consumer. It uses management HTTP with explicit private-target/TLS permission and never invokes master-local egress, core validation or restart. Failed fetches preserve the cache; failed compilation and manual drafts preserve the applied graph. New APPLIED publications retain a durable wake even after a refresh cursor has passed them.

`RunFleetProviderSchedulers` is not installed in the role factory. The supported candidate feed subset is strict line/base64 lists containing VMess, VLESS, Trojan or Shadowsocks entries. Other existing protocols/formats, provider CRUD exposure, and final integration qualification remain factory gates. The old mutable subscription routes are not silently migrated or redirected. Exact publication, source pins, same-deployment receipts, Stop carry-forward, and quota-preserving refresh contracts are recorded in [node-provider-refresh.md](node-provider-refresh.md).

Automatic source enable and placement removal require an explicitly APPLIED network baseline too. The actual resolved node/default revisions, deployment payload hash and receipt must match that approved baseline; a saved manual draft or an initially unpublished network remains a dependency hold. Required source stops still advance. A fully stopped enabled source may commit derived materialization while retaining `NETWORK_APPROVAL_REQUIRED` on pending source work, allowing an administrator to Preview, Publish and wait for APPLIED. This hold neither approves the placement nor starts billing or grants credit. Superseding source mutations clear the old progress diagnostic, and only actual later convergence completes the work.

The owned source reader returns the current actor, logical and panel client identities, revision, raw common client fields, plan assignment/override flags, explicit and effective template memberships, per-binding credential values/flow, external links and durable client progress from one repeatable-read, read-only transaction. It does not hydrate common credentials from a selected inbound. Each stored binding is marked effective, retained or unknown. An unresolved dependency yields `effectiveScopeKnown=false` and `effectiveInboundIds=null`; a known empty set is `[]`. These are desired-source fields for editing/export, not a public subscription projection or evidence that a node has applied them. The reader checks the bound database lifecycle before and after the snapshot and rejects oversized aggregate credential storage before fetching values.

Tests must use `httptest` and real PostgreSQL revision transactions: redirects and private targets honor policy, an interrupted fetch retains the old revision, concurrent refreshes cannot overwrite newer revisions, only inheriting nodes are targeted, and no master-local egress/core call occurs.

## Statistics notifications

`StatsNotifyJob` gates reports on local Xray liveness. Removing that gate alone is insufficient: `Tgbot.SendReport` calls local `ServerService.GetStatus`, reads shared legacy presence, and builds quota/exhaustion notices from normalized `client_traffics`. It can therefore describe the master host as a serving node or report old accounting views.

`service.ReadFleetStats(ctx, db, now)` reads an independent repeatable-read, read-only snapshot of the approved ledger projection, normalized notification membership, settings and fleet observations. Nested transactions are refused. A one-minute deadline bounds the snapshot read. It folds all client counts and measured/opening totals while paging 128 clients at a time, retaining only notification candidates; associated node observations are loaded in batches. Reservations are never added to measured totals. Node contact, report receipt and observation timestamps are distinct, and old, future or foreign-session observations cannot establish readiness. Management host identity/version is separate from serving-node state; no local Xray status or legacy presence is consulted.

`tgbot.SendFleetReport(ctx, db)` retains configured administrator recipients and deduplicated non-admin Telegram client notices. A client chat must have an enabled inbound attachment; it receives its own near-limit clients and disabled-client list only when a near-limit notice exists. Unknown reserved/uncertain values remain unknown. The scheduled Telegram backup flag uses the management database dump and existing archive sender, explicitly excluding agent state/runtime credit journals and avoiding the legacy local-Xray configuration backup. Delivery and backup failures are returned to the job.

`job.NewFleetStatsNotifyJob(ctx, db)` takes the host lifecycle context and prevents overlapping runs. The factory must cancel the old context before restore and recreate the callback with the replacement handle. Snapshot reads, dump generation and every message/archive send check cancellation; the exact current database pool is checked before and after snapshot/dump and before each send. `GetDbContext` binds the dump process to this lifecycle while the legacy `GetDb` behavior remains unchanged.

Reports have an initial bound of 4,096 retained notification candidates and 1,024 node rows. Exceeding either returns `ErrFleetStatsCapacity` before any recipient receives a partial report; no recipient is silently truncated. Aggregate counts/totals are independent of retained candidates. This bounds memory, but scanning a large fleet inside the snapshot and delivering notices every minute still require a separate scale qualification. The callback is not yet installed in the main factory; role startup remains gated by the other business prerequisites and final qualification.

Tests must build reports from committed measurements and stale/offline observations, prove that reservations do not increase measured totals, and preserve ordinary notification recipient policy. No messages should be sent during qualification: use the existing message-sender test seam.

## Frontend management checkpoint

Client traffic schemas retain authoritative fleet accounting metadata. Quota, expiry and status displays use the authorized term while editors preserve normalized source values. Measured usage, opening balances, reservations, unknown amounts and reported daily history remain distinct.

`ClientInfoModal` exposes shared reset scheduling only when fleet accounting supplies the immutable `clientId` and the authenticated `/me` query identifies an administrator. It uses generated request/view schemas, inherits the applied plan or selects an explicit cadence, displays server-provided UTC anchors and boundaries, and keeps pending reset policy read-only. A revision-zero inherited view can be explicitly initialized. Cancellation requires confirmation and explains preserved allowance/reservations, skipped missed intervals and mandatory node stops.

Before either mutation, the exact operation UUID and body are retained in actor/client-scoped session storage. There is no automatic POST retry. An unconfirmed response permits an explicit identical retry or a fresh GET; only a newer schedule revision reconciles that uncertainty without a confirmed POST response. Cleanup compares the retained request before deleting it, so a late response cannot erase a newer request after the modal is reopened. Unavailable storage, identity mismatch or a failed read blocks new changes.

The reset UI passes 15 focused component tests, seven Chromium stories with light/dark accessibility checks, five schema/i18n checks, strict typecheck, and lint with zero errors and the existing unrelated warning. Ten removed-safeguard controls reproduce their intended failures. The complete frontend gate subsequently passed 2,364 tests in 268 files, including 248 Chromium stories and the final cross-tab creation actor fence. These controls do not enable the gated backend factory or provide a node UI.

Single-client creation checks the actual runtime capability before choosing the owned API or the temporarily supported ordinary path. An unavailable capability is not ordinary support. Owned creation sends client, plan overrides, scoped credentials and external links in one transaction; the page does not perform a second external-links write. Protocol-specific automatic credentials remain per binding, and explicit supplied credentials are not silently rotated when templates change.

The exact secret-bearing creation body exists only in memory. Session storage contains actor-scoped operation UUIDs, including unresolved older requests. An uncertain response permits an identical retry while that body exists or a receipt lookup after reload. Starting a different request requires explicit confirmation and retains the older receipt locator; a failed response or missing receipt never proves that an earlier request cannot commit. Actor changes and unmount clear retry material, and lifetime/locator comparisons prevent late responses from clearing newer work.

Capability and receipt responses must identify the captured actor. Owned POSTs carry an expected actor that the server checks before dispatch: another tab changing the session cannot create under a different administrator while leaving the recovery locator under the old one. Refreshing the account query alone is insufficient because the cookie can change between that read and the POST.

Creation qualification includes 14 focused hook/component tests, 23 client Chromium stories, 19 removed-safeguard controls, strict typecheck, and full ESLint with zero errors and the existing unrelated React Hook Form warning. The embedded Vite bundle and static Storybook build pass, with unchanged OpenAPI generation hashes. Owned edit, bulk, import, reseller and LDAP creation remain separate integration work; this checkpoint does not activate the master factory.
