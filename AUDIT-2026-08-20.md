## The one fix that changes the most

Nine of the findings below share a single root cause, and fixing it converts all of them from
*"the whole server goes offline until someone edits the DB"* into *"the save is refused with an
error"*:

**`RestartXray` stops the running process before it knows the new config is valid**
(`internal/web/service/xray.go:1127`), and **nothing validates a generated config against
xray-core's own builders before it is written** (F004). xray-core validates atomically — one
bad inbound aborts the whole load — so any single malformed row takes down every inbound of
every protocol on the box. Worse, the bad row is already persisted, so every subsequent restart
fails identically.

The panel already vendors the builders and already uses them on two narrower paths
(`ValidateOutboundConfig`). Extending that to inbounds and pre-flighting the whole config before
`process.Stop()` is the highest-leverage change in this report.

Findings it de-fangs: **F014** (Critical), **F073** (Critical), F002, F005, F052, F064, F320,
F321, F186.

### F073 — Routing compile emits one pex<id> outbound per (rule,subject) pair — duplicate tag stops Xray booting

**`internal/routing/plan.go:166`** · also `internal/routing/plan.go:270`, `internal/web/service/routing.go:305`, `internal/routing/plan.go:322`  
*Area:* outbounds/egress — routing compile → xray outbounds · *Verdict:* CONFIRMED

> ```
> 			if outbound != nil {
> 				out.Outbounds = append(out.Outbounds, outbound)
> 				out.NeedsRestart = true
> 			}
> ```

**What.** Plan() loops subjects, then that subject's rules, and appends compileRule's synthesized outbound every time. For DestExit the synthesized outbound's tag is exitOutboundTag(exit.ID) = "pex<id>" — a pure function of the EXIT, not of the (rule,subject) pair. So N (rule,subject) pairs pointing at one exit produce N byte-identical outbound objects, all tagged pex<id>. applyRoutingPlan then concatenates them into cfg.OutboundConfigs with no dedupe (internal/web/service/routing.go:303-313).

**Why it matters.** xray-core's outbound Manager.AddHandler returns `errors.New("existing tag found: " + tag)` on a duplicate tag (app/proxyman/outbound/outbound.go), addOutboundHandlers propagates it, and core.New fails — Xray refuses to start. RestartXray has already called process.Stop() by then (internal/web/service/xray.go:1127), so the panel is left with no core at all: every client of every inbound, on every protocol, drops. Minimal trigger, both first-class uses of the feature: (a) ONE routing rule whose ingressIds names two inbounds and whose destination is an exit; (b) TWO rules on one inbound both pointing at the same exit; (c) a scope="all" rule with an exit destination on a host with two routable inbounds. It works only with exactly one (rule,subject) pair, which is why the existing test TestSocksExitSynthesizesItsOutbound (internal/routing/plan_test.go:326) passes.

**Fix.** Emit each exit's outbound at most once. In Plan(), keep a `emittedOutbounds := map[string]bool{}` (or key by exit ID) and skip the append when the tag is already present; alternatively have compileRule return the exit ID and collect the set, materialising the outbounds once at the end. Belt-and-braces: make applyRoutingPlan drop a compiled outbound whose tag already exists in `outbounds`.

**Test.** Go table test in internal/routing/plan_test.go: Plan(Input{Subjects: two internal subjects, Rules: one enabled rule with IngressIDs [1,2] and Dest{Kind: DestExit, ExitID: 4}, Exits: one ExitDevice/SourceOwnerDaemon exit id 4}) and assert len(got.Outbounds) == 1 and that the decoded tags are unique. Revert the fix and it must go red with 2.

### F014 — Shadowsocks 2022-blake3-chacha20-poly1305 + any client makes xray-core reject the whole config

**`internal/database/model/model.go:623`** · also `internal/xray/api.go:496`, `internal/xray/shadowsocks.go:60`, `internal/sub/service.go:941`, `frontend/src/pages/inbounds/form/protocols/shadowsocks.tsx:27`  
*Area:* share-link / client-config consistency (shadowsocks) · *Verdict:* CONFIRMED · *Independently reported as* F003, F320 · *needs a runtime check*

> ```
> //   - Shadowsocks 2022 (2022-blake3-*): xray's multi-user code rejects the
> //     inbound with "users must have empty method" when a client carries
> //     one — strip stale entries left over from a switch off a legacy
> //     cipher.
> ```

**What.** The panel treats every `2022-blake3-*` cipher as multi-user: it keeps a `clients` array, mints a per-client 32-byte key (internal/xray/shadowsocks.go:60 gives 2022-blake3-chacha20-poly1305 a key size), strips the per-client `method` (model.go:655) and emits a multi-user share link `method:serverKey:clientKey` (internal/sub/service.go:941-945). The cipher is offered in the inbound form's Select (frontend/src/pages/inbounds/form/protocols/shadowsocks.tsx:27). But xray-core's `buildShadowsocks2022` rejects a users/clients array for any non-AES 2022 cipher: `if !strings.Contains(v.Cipher, "aes") { return nil, errors.New("shadowsocks 2022 (multi-user): only blake3-aes-*-gcm methods are supported") }` (module cache: xtls/xray-core@v1.260327.1/infra/conf/shadowsocks.go:126-127; the underlying sagernet/sing-shadowsocks@v0.2.9/shadowaead_2022/service_multi.go:50-56 only accepts the two AES methods).

**Why it matters.** An admin picks `2022-blake3-chacha20-poly1305` from the inbound form (or switches an existing SS inbound onto it) and attaches one client. The generated xray config now fails to load. internal/cores/internal/xray/core.go:121-127 stops the running process (`_ = process.Stop()`) BEFORE starting the replacement, so the rejected config takes the entire core down — every inbound of every protocol on that box, not just the shadowsocks one. Nothing in the panel validates the pairing: HealShadowsocksClientMethods only strips per-client `method`, and the TypeScript-only `isSSMultiUser` predicate (which does know chacha20 is single-user) is never consulted by any Go path.

**Fix.** Add the pairing to internal/core/capability.go as a rule (e.g. CapSSMultiUser: protocol==shadowsocks AND NOT settings.method in ["2022-blake3-chacha20-poly1305"]) so Go and TS read one table, then reject at inbound save/client attach: in internal/web/service/client_crud.go refuse to attach a client to a shadowsocks inbound whose method is 2022-blake3-chacha20-poly1305, and in the inbound update path refuse a method switch onto it while clients exist. Smallest safe stopgap: drop 2022-blake3-chacha20-poly1305 from SSMethodSchema (frontend/src/schemas/protocols/shared/shadowsocks.ts) and from internal/xray/api.go's shadowsocks2022Ciphers, since the panel is inherently multi-client.

**Test.** On the penhoon VM: create a shadowsocks inbound with method 2022-blake3-chacha20-poly1305, attach one client, restart the panel, then `journalctl -u p-ui` / the panel's xray log. Expect xray to exit immediately with `shadowsocks 2022 (multi-user): only blake3-aes-*-gcm methods are supported` and every inbound to stop answering. Go test: table-driven case in internal/web/service asserting that attaching a client to that method returns an error instead of writing settings.

### F287 — Any Telegram user can read any client's subscription URL and configs via a forged callback

**`internal/web/service/tgbot/tgbot_router.go:1511`** · also `internal/web/service/tgbot/tgbot_router.go:1543`, `internal/web/service/tgbot/tgbot_client.go:229`, `internal/web/service/tgbot/tgbot_client.go:251`, `internal/web/service/tgbot/tgbot_client.go:334`  
*Area:* tgbot: callback authorization · *Verdict:* CONFIRMED · *Independently reported as* F203

> ```
> 		if after, ok := strings.CutPrefix(callbackQuery.Data, "client_sub_links "); ok {
> 			email := after
> 			t.sendClientSubLinks(chatId, email)
> 			return
> ```

**What.** isClientSelfCallback() whitelists the PREFIXED forms `client_sub_links <email>`, `client_individual_links <email>` and `client_qr_links <email>` as "per-user client actions that resolve their own data from the caller's Telegram id" (its own doc comment, tgbot_router.go:1534-1536). They do not. The default branch at 1511-1525 splits the caller-supplied email straight out of the callback payload and calls sendClientSubLinks / sendClientIndividualLinks / sendClientQRLinks with it. Those three functions call buildSubscriptionURLs(email) -> inboundService.GetClientByEmail(email) and never compare the resolved client's TgID with callbackQuery.From.ID. The bare, safe forms (`client_sub_links` with no argument) DO resolve from From.ID via GetClientTrafficTgBot; the prefixed forms are the exact opposite and are gated by the same predicate.

**Why it matters.** Callback payload is attacker-chosen text, not a trusted button press. Telego's own type doc states it: "Data - Optional. Data associated with the callback button. Be aware that the message originated the query can contain no callback buttons with this data." (types.go:3652). Any Telegram user who has ever received an inline keyboard from the bot (the bot answers /start from anyone and hands non-admins a keyboard via SendAnswer's numericKeyboardClient) can issue a callback carrying `client_individual_links victim@example.com` and receive the victim's full vless://UUID@host / trojan://password@host URIs and QR codes, plus the subscription URL containing the SubID token. That is the complete credential set for another operator's client. Precondition: the attacker must know or guess the target email; emails are operator-chosen and commonly human-readable (there is no character or format validation anywhere - see the absence of any email pattern check in client_crud.go / client_inbound_apply.go, which only reject duplicates).

**Fix.** Delete the three HasPrefix cases from isClientSelfCallback (tgbot_router.go:1543-1545) so only the argument-less self-resolving callbacks stay non-admin, and in the default branch resolve ownership before serving: for a non-admin, look the email up in inboundService.GetClientTrafficTgBot(callbackQuery.From.ID) and refuse if it is not in that set. Concretely, pass isAdmin into the default branch and guard each CutPrefix case with `if !isAdmin && !t.ownsEmail(callbackQuery.From.ID, email) { return }`.

**Test.** Go test in package tgbot, no DB needed for the predicate half: assert isClientSelfCallback("client_sub_links alice@x") == false (this is the inverse of the current TestIsClientSelfCallback assertion at tgbot_callback_auth_test.go:28). For the end-to-end half, an initSubDB-style Postgres test that seeds two clients with different tgId values, calls answerCallback(&telego.CallbackQuery{Data: "client_individual_links victim@x", From: telego.User{ID: attackerID}, Message: ...}, false) with a stub send sink, and asserts nothing containing the victim's SubID or UUID was emitted.

### F095 — HeaderProtectionKey with any unset S1..S4 is accepted, then half-applied by the kernel

**`internal/awg/params.go:142`** · also `third_party/amneziawg-kernel/src/netlink.c:956`, `third_party/amneziawg-kernel/src/netlink.c:968`, `internal/cores/internal/amneziawg/share.go:100`, `internal/web/service/inbound.go:1084`  
*Area:* AWG · *Verdict:* CONFIRMED

> ```
> 			if padding.value > 0 && padding.value < HeaderProtectionNonceSize {
> ```

**What.** Validate() only rejects a padding value that is non-zero and below 12. It deliberately lets S1..S4 == 0 pass when a HeaderProtectionKey is set. The vendored module does the opposite: third_party/amneziawg-kernel/src/netlink.c:953-979 checks the MERGED device state (wg->init_padding, wg->resp_padding, wg->cookie_padding, wg->transport_padding) and returns -EINVAL when ANY of the four is below HEADER_PROTECTION_NONCE_SIZE. Zero is below 12, so an unset S3 or S4 is a refusal, not a default. Worse, the refusal happens AFTER the same wg_set_device call has already written jc/jmin/jmax (netlink.c:799-806), S1/S2 (808-830) and H1..H4 (865-911) into the device -- the `goto out` at 959 does not roll any of that back.

**Why it matters.** The inbound form ships a HeaderProtectionKey field (frontend/src/pages/inbounds/form/protocols/awg-obfuscation.tsx:100) and a one-click preset that sets only jc/jmin/jmax/s1/s2 -- s3 and s4 stay 0. An operator who fills in a 32-byte key and saves gets: the panel's Validate passes, the netlink SET partially applies and returns EINVAL, and every client .conf the panel hands out carries `HeaderProtectionKey = ...` (internal/cores/internal/amneziawg/share.go:100) that the server never installed. Header protection encrypts the message header the server parses first, so the server cannot recognise a single packet from any client: zero handshakes, forever, on every client of that inbound. And it is silent -- the apply runs post-commit and only logs at debug level (internal/web/service/inbound.go:1080-1086), so the panel reports the inbound as saved successfully.

**Fix.** Drop the `padding.value > 0 &&` guard so the check becomes `if padding.value < HeaderProtectionNonceSize` whenever HeaderProtectionKey != "" -- that is exactly what netlink.c:956-979 enforces. Then the refusal names the missing field before anything is written.

**Test.** Go table test in internal/awg/params_test.go: Params{HeaderProtectionKey: <valid 32-byte base64>, S1: 20, S2: 30} must return ErrPaddingTooSmall naming s3. Revert the guard and confirm it goes green (proving the test bites). Runtime confirmation on the VM: `awg set pawg4 <hpk> s1 20 s2 30` and read dmesg for "S3 must be more then 12 to use headerProtection".

### F098 — Saving an AmneziaWG inbound in the UI silently strips h1..h4 and every timer param

**`frontend/src/schemas/protocols/inbound/awgkernel.ts:19`** · also `frontend/src/pages/inbounds/form/InboundFormModal.tsx:535`, `frontend/src/lib/xray/inbound-from-db.ts:26`, `internal/awg/encode.go:99`  
*Area:* AWG · *Verdict:* CONFIRMED

> ```
> export const AwgParamsSchema = z.object({
> ```

**What.** AwgParamsSchema omits h1..h4, contentPaddingAddition and every rekey/keepalive timer -- deliberately, per its own comment ('they stay settable through the API'). But zod v4 z.object strips unknown keys, and InboundFormModal saves the PARSED output: `const payload = formValuesToWirePayload(parsed.data)` (InboundFormModal.tsx:535) where parsed comes from InboundFormSchema, which is InboundFormBaseSchema.and(...).and(InboundSettingsSchema) (frontend/src/schemas/forms/inbound-form.ts:56-58). So any h1..h4 set through the API is deleted from settings the first time anyone opens and saves that inbound in the panel. inboundFromDb does the same strip on the read side (frontend/src/lib/xray/inbound-from-db.ts:26-29), so the frontend link and QR never carry them either.

**Why it matters.** The device does not lose them at the same time: encodeParams skips zero-valued attributes (internal/awg/encode.go:98-101, `if value != 0`), and an absent attribute means 'leave it alone' to the module. So after an innocuous edit -- renaming the inbound, changing its port -- the kernel device still uses H1..H4 = the operator's custom ranges while every .conf and link the panel now hands out has none, and clients silently fall back to WireGuard's 1/2/3/4. Every client of that inbound stops connecting, and nothing anywhere says an edit did it. It also means a custom header can never be cleared through the panel at all.

**Fix.** Add h1..h4 (and the timers) to AwgParamsSchema as `z.string().optional()` -- they already cross the API as range text like "10-19" via internal/awg/params_json.go -- so the round-trip preserves them. Separately, have Params.Validate/encodeParams distinguish 'absent' from 'zero' (e.g. carry pointers, or always emit H1..H4 once any of them is set) so a cleared header actually lands on the device.

**Test.** Vitest: feed rawInboundToFormValues an awgkernel row whose settings contain `"awg":{"jc":4,"h1":"10-19"}`, run it through InboundFormSchema.safeParse + formValuesToWirePayload, and assert the emitted settings JSON still contains h1. It fails today. Go side: internal/awg/encode_test.go asserting a Params with H1=0 after a device held H1=HeaderRange(10,19) produces an attribute that resets it.

### F266 — A kernel-refused AmneziaWG obfuscation edit is reported to the operator as a successful save

**`internal/web/service/inbound.go:1534`** · also `internal/web/service/inbound.go:1083`, `internal/cores/internal/amneziawg/core.go:90`  
*Area:* awgkernel apply error surfacing · *Verdict:* CONFIRMED

> ```

> 							if newProtocolServedByXray {
> 								needRestart = true

**What.** postCommitApply runs rt.UpdateInbound after the transaction commits. ### F042 — Traffic-reset paths never clear a depletion disable, so reset clients stay cut off at the core

**`internal/web/service/client_traffic.go:173`** · also `internal/web/service/client_traffic.go:213`, `internal/web/service/inbound_disable.go:221`, `internal/web/service/xray.go:259`, `internal/web/service/inbound.go:1687`  
*Area:* client limits / traffic reset · *Verdict:* CONFIRMED · *Independently reported as* F107, F117, F244

> ```
> 		result := tx.Model(xray.ClientTraffic{}).
> 			Where("email IN ?", resetEmails).
> 			Updates(map[string]any{"enable": true, "up": 0, "down": 0})
> ```

**What.** resetAllClientTrafficsLocked (the periodic hourly/daily/weekly/monthly reset job) and ClientService.ResetAllTraffics (the Clients page "Reset all traffics" button) zero usage and flip client_traffics.enable back to true, and nothing else. But the depletion pass disables a client in THREE places: client_traffics.enable, clients.enable (inbound_disable.go:221 `Updates(map[string]any{"enable": false, ...})`) and the inbound settings JSON entry["enable"]=false (markClientsDisabledInSettings, inbound_disable.go:271). The config builders read the last two: RenderInbound skips `if !c.Enable { continue }` (xray.go:259, c.Enable comes from clients via ListForInbound) and buildInboundForLocalRuntime skips `if manualEnable, ok := c["enable"].(bool); ok && !manualEnable` (inbound.go:1687). Neither reset path rewrites either one, and SyncInbound re-asserts the stale false (applyClientRecordMerge sets row.Enable = incoming.Enable unconditionally, client_link.go:53).

**Why it matters.** A client who exhausts totalGB on the 10th of the month is disabled by disableInvalidClients. On the 1st the monthly PeriodicTrafficResetJob fires, zeroes their usage and re-enables their client_traffics row — and the client still cannot connect, on every protocol (xray kinds via RenderInbound, wgkernel/mtproto via buildInboundForLocalRuntime->DesiredInstances). An xray restart does not help because the restart rebuilds from the same RenderInbound. The panel's clients list also still shows them disabled (client_paging.go uses COALESCE(c.enable, FALSE) off the clients table), so the operator sees a contradiction: quota reset, client dead. Recovery needs a manual per-client enable or a per-client reset. Monthly quota cycles are the single most common billing model for this panel, so this is hit by ordinary use. Contrast the paths that get it right: ResetTrafficByEmail (client_traffic.go:30-43) and BulkResetTraffic (client_traffic.go:85-98) both call s.Update with Enable=true, which rewrites the settings JSON and the clients row and re-adds the user at the runtime.

**Fix.** Make both reset paths restore the same three flags the depletion pass cleared, but only for clients that were disabled BECAUSE they were depleted — `enable=false` also means admin-disabled and must survive a reset. Reuse the in-repo pattern from BulkAdjust (client_bulk.go:443-531): before zeroing, collect the emails matching `depletedCond(db) AND enable = false`; after zeroing, re-check which are no longer depleted and drive those through s.BulkSetEnable(inboundSvc, reEnable, true) so clients.enable, the inbound settings JSON and the runtime all converge. That also replaces the blanket `"enable": true` write on client_traffics in resetAllClientTrafficsLocked/ResetAllTraffics, which today silently re-enables admin-disabled clients at that one layer.

**Test.** Go test in internal/web/service against a throwaway Postgres (template: internal/sub initSubDB / global_traffic_test.go): create a vless inbound with one client (total=1GB), write client_traffics up+down >= total, call svc.disableInvalidClients(db), assert clients.enable==false and settings JSON enable==false; then call clientSvc.ResetAllClientTraffics(&inboundSvc, inbound.Id); assert clients.enable==true AND that XrayService.RenderInbound(inbound) emits the client in settings.clients. Revert the fix and the RenderInbound assertion must go red.

### F226 — awgkernel: a cleared obfuscation parameter is never pushed to the kernel device

**`internal/cores/internal/amneziawg/core.go:105`** · also `internal/awg/encode.go:88`, `internal/cores/internal/amneziawg/share.go:64`, `frontend/src/schemas/protocols/inbound/awgkernel.ts:21`  
*Area:* cores/amneziawg + inbound edit · *Verdict:* CONFIRMED · *Independently reported as* F265

> ```
> 	if params.IsZero() {
> 		return nil
> 	}
> ```

**What.** Applying an awgkernel inbound pushes obfuscation with `awg.ConfigureParams`, but (a) `applyParams` returns early when the whole Params struct is zero, and (b) `encodeParams` emits an attribute only when the field is non-zero (`u16 := func(kind uint16, value uint16) { if value != 0 {...} }`, encode.go:88-92). Zero therefore means "leave the kernel's current value alone", never "set it back to zero". The device is not recreated on an edit either — `Manager.ensureLocked` reuses the existing link (internal/wireguard/manager.go:336-357) — so nothing ever clears a parameter that was previously set.

**Why it matters.** The client half of the same parameter IS cleared: `insertParams` writes a key only when the value is non-zero (share.go:63-66), so the .conf the panel hands out after the edit omits S1/S2/S3/S4/H1..H4 entirely. ## Honest limits of this audit

- **Static only.** 39 findings are marked as needing a runtime check. The highest-value ones to
  run on the VM first: F014 and F073 (does the core really fail to start?), F335 (does an
  established session really survive `RemoveUser`?), F151 (`ls -ln /usr/local/p-ui/p-ui` after a
  release install), and F226 (`awg show` after clearing a parameter).
- **8 findings are PLAUSIBLE, not confirmed** — marked `~` in the tables.
- **Deduplication was conservative.** The automatic key collapsed 413 → 412; the 12 duplicate
  clusters in the Critical/High set were merged by hand and are annotated. The Medium and Low
  tables may still contain near-duplicates at adjacent lines.
- **Severity is calibrated to a public, self-hosted panel** where a fresh install is directly
  exposed. "Critical" means auth bypass, data destruction, or a state where a single ordinary
  operation makes the whole box stop serving.
- **The 714 verified-correct entries are the coverage proof**, not filler — they record what was
  actively traced and found right, so the absence of a finding in an area can be read as
  evidence rather than as silence.
